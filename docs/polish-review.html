Four renders is what the arithmetic predicts: 270px of travel, 103px of margin, re-centring on each render, plus one for the direction reversal. The blit is byte-identical to the source sub-rect — 0 pixels differ — once the camera snaps to whole device pixels.

What a blit is not

I tried to prove the sub-rect pixel-identical to a fresh render. It is not, and the reason is worth stating rather than papering over: canvas 2d rasterisation is not translation invariant. Shifting the scene by a single device pixel already changes anti-aliased coverage on diagonal edges, and an isometric scene is almost nothing but diagonal edges.

Measured at 1.4–2.1% of pixels, mean 15 summed across RGB, with 93% of them sitting on a shape edge. Rendering the same input twice is byte-identical, so the layer itself is deterministic. Before the camera snap the fractional-offset case was 27% of pixels at mean 40 — that one was a real artefact, and it is gone.

Three things that bit me, and what they cost

The vine pushed the page open. You saw it before I did: “the bottom of the page keeps expanding downwards, as if the page is falling”. A canvas is a replaced element, so its intrinsic size is its width/height attributes — and paint() set those from clientHeight × devicePixelRatio while the canvas sat in normal flow. Each paint multiplied the box by the pixel ratio. At devicePixelRatio 1 the multiplier is exactly 1.0, a fixed point that never moves, which is why every check I ran missed it: the browser pane runs at dpr 1 and your Mac does not. There was 42,652px of residue sitting in the page when I went looking. Fixed by taking the canvas out of flow — and inset: 0 alone was not enough, because for an absolutely positioned replaced element height: auto resolves to the intrinsic height and bottom is dropped as over-constrained.

The first palette lock made the train sim worse. I clustered colours weighted by how often each is written in the source. The terrain collapsed into grey-olive, because a grass colour appears once in a palette array and covers 33% of the canvas while a window highlight appears once and covers four pixels. Reverted, re-weighted from a histogram of the rendered canvas, and the palette now spends 77.6% of its slots where the pixels actually are.

Two harnesses were lying. The flora harness tested settled before the first tick, so it reported a 12-segment garden as though that were the design; and its constant rewriting used a plain string replace, so once the module was retuned the sweep silently stopped substituting and printed twenty identical rows as twenty experiments. Both now fail loudly.

function weekdaysAfterUpTo(a, b) {
  const days = Math.round((b - a) / 86400000);
  const weeks = Math.floor(days / 7);
  let count = weeks * 5;
  const cursor = new Date(a);
  cursor.setDate(cursor.getDate() + weeks * 7);
  for (let i = weeks * 7; i < days; i += 1) {
    cursor.setDate(cursor.getDate() + 1);
    if (isWeekday(cursor)) count += 1;
  }
  return count;
}

The colony gets more expensive as it grows

measuredexponent unproven effort: S–Limpact: high on phones

This is the best candidate I found for "over time it happens". The ant model's cost grows sharply with colony size, and the colony grows the longer the page is open. Drawing does not: it is flat.

measured on this Mac, model vs draw
antsmodel ms/sdraw ms/sspread (worst/median)
34.114.31.4×
1137.714.11.6×
2158.614.62.8×

Drawing is flat because it rasterises the same canvas whatever is on it. The model is not. Somewhere around 8–10 ants the model overtakes rendering and keeps going.

what this means off this machine

58 ms of CPU per wall-clock second is 6% of one core on an M5 Pro. A mid-range phone is roughly 10× slower on single-thread JS, which puts the same colony at ~60% of a core, continuously, before drawing, the page, or the browser.

And the simulation uses a fixed-timestep accumulator. When it cannot keep up it runs more updates per frame to catch up, which costs more, which makes it fall further behind — bounded only by the MAX_DELTA clamp, at which point the colony visibly slows down rather than stopping. That is what "chugs" looks like.

what I could not establish, and why
  • The complexity class. Two runs gave exponents of 1.92 / 1.87; a third gave 1.71 / 0.68. I will not call it O(n²) on that evidence.
  • Which phase is hot. I tried stubbing phases and comparing. That method is invalid here: the model is stateful, so removing a phase changes the trajectory and the next updates do different work. The negative "shares" it produced are the giveaway.
  • I found an O(n²) shape and it was a red herring. rebalanceTasks runs a find whose predicate does a filter inside a while whose condition is another filter — textbook quadratic. It measured at roughly 2–6% of model cost, because it only runs every 1.5 simulated seconds and exits early when the allocation is already balanced. Worth tidying; not the cause.
  • The environment. The preview pane throttles rAF to ~4 fps and the timing variance was large. Every number above is an order-of-magnitude claim, not a benchmark.
